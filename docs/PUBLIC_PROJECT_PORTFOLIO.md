## Promotion rule

A program should move to a stronger public maturity label only when resolving evidence exists for the promoted claim.

Examples of resolving evidence may include:

- running implementation with reproducible setup;
- tests and CI that exercise the claimed behavior;
- architecture and threat model;
- sample output that does not expose protected data;
- verification notes and limitations;
- approved public demonstration;
- documented deployment or adoption evidence when such a claim is made;
- customer or partner evidence only when publication is authorized.

## Repository documentation target

Each material project should converge on the applicable parts of this documentation set:

1. `README.md` — purpose, current reality, quickstart, maturity, boundaries.
2. `AGENTS.md` — agent/automation governance where automated systems can act.
3. `SECURITY.md` — vulnerability handling, secret handling, authorization, threat assumptions.
4. `docs/architecture/` — components, data flows, trust boundaries, dependencies.
5. `docs/runbooks/` — startup, shutdown, health, backup, restore, rollback, recovery.
6. `docs/status/` or roadmap — verified, in-development, blocked, next gates.
7. tests / CI — where meaningful.
8. provenance / limitations — evidence, uncertainty, public/private boundaries.

## Public engagement mapping

The portfolio is not the public menu by itself. External conversations are routed through the smaller set of outcome-oriented paths on PQExpert:

- cyber resilience and security-operations modernization;
- post-quantum readiness;
- technical strategy and executive briefing;
- prime / lab / research support;
- hiring / embedded operator conversations.

The underlying program used for a scoped engagement is selected after the need, authorization, risk, and evidence requirements are understood.
